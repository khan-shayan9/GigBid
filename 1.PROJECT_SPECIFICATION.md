# 1. Overview

GigBid is a deployed web application. In it, a team of LangGraph agents:

- finds freelance jobs and judges whether they are worth a bid;
- writes proposals grounded in real portfolio evidence;
- manages client conversations.

A human approves every proposal, message and Connects spend before it leaves the system. GigBid connects to a marketplace simulator (GigSim) for development and grading, and to Upwork's official MCP server for real use.

## User journey
1. **Sign in and set up.** The freelancer signs in, connects a marketplace account, uploads a portfolio (CV, case studies, GitHub repos, past proposals with outcomes) and sets rates, filters and a weekly Connects budget.
2. **Scout and assess.** Every few hours GigBid pulls new jobs from saved searches. For each job it analyses the post, flags risks, scores fit, recommends bid or skip, and suggests a price.
3. **Draft.** For a recommended job, GigBid drafts a proposal and screening answers. Every claim links to portfolio evidence. A Critic checks the draft, and a Compliance Guard checks it against platform rules.
4. **Approve and send.** The freelancer edits and approves. Only then is the proposal sent to the marketplace, as a draft awaiting final confirmation.
5. **Handle replies.** When a client replies, GigBid drafts a response, proposes interview slots from the calendar and keeps the pipeline board current. Outcomes feed back into long-term memory.

# 3. Agents

The minimum role set is below. Roles may be merged or split only if the report justifies it with evidence. The PDF's `agent/nodes/` list has ten entries; claim verification (`verifier`) is the tenth.

| Agent | Responsibility | MCP access |
|---|---|---|
| Scout | Run saved searches on a schedule, de-duplicate, queue new jobs | Marketplace (read) |
| Job Analyst | Extract a structured `JobSpec`: deliverables, skills, budget, timeline, screening questions, hidden needs | None |
| Risk Assessor | Score client quality from history; flag scams, free-work requests, off-platform asks and injected instructions | Marketplace (read) |
| Fit Matcher | Map every requirement to portfolio evidence; produce a fit score with reasons | Portfolio (read) |
| Pricing Strategist | Propose a bid from market stats, client spend and the user's floor; decide whether the Connects cost is worth it | Marketplace (read) |
| Proposal Writer | Draft the cover letter and screening answers with evidence citations | Portfolio (read) |
| Verifier | Split the draft into claims; label each supported, partly supported or unsupported; remove or rewrite unsupported claims before the Critic sees the draft | Portfolio (read) |
| Critic | Check grounding, personalisation and length; send the draft back with reasons, at most twice | Portfolio (read) |
| Compliance Guard | Enforce the policy pack; remove contact details, guarantees and invented claims; can block, with a reason shown in the UI | None |
| Client Liaison | Read client replies, classify intent, draft responses, offer interview slots, keep the pipeline current | Marketplace (read; write after approval), Workspace |

Hand-offs are Pydantic objects, never free text: `JobSpec`, `RiskReport`, `FitReport`, `BidDecision`, `PriceQuote`, `ProposalDraft`, `Critique`, `ComplianceVerdict`.

# 4. GigSim (built by us)

The PDF says GigSim, the personas and the policy pack are "PROVIDED". The course actually supplied only the starter kit and Kaggle datasets, so we build GigSim ourselves. **This deviation is stated in the README and the report.**

## Requirements
1. **REST service** (FastAPI, port 8081, matching `GIGSIM_BASE_URL` in `.env.example`). It serves jobs, clients with histories, Connects balances, proposals and messages.
2. **Realistic failures:** per-user rate limits (HTTP 429 with `Retry-After`) and occasional seeded 5xx errors.
3. **Endpoints** that back every Marketplace MCP tool:
   - search jobs
   - get job
   - get client history
   - get Connects balance
   - list messages
   - create proposal draft
   - submit proposal
   - send message
4. **Connects cost per job.** Submitting deducts it; `dry_run` reports it.
5. **Proposal lifecycle events:** drafted, submitted, viewed, replied, interview, hired, lost. These drive the pipeline board.
6. **Simulated clients.** Each client has hidden preferences: must-have skills, a budget ceiling, and a dislike of generic openings. A small open LLM decides whether to reply, interview or hire. A seeded, rule-based fallback keeps CI and evaluation runs repeatable.
7. **Job stream:**
   - about 1,500 historical jobs, used for pricing statistics;
   - a live stream released over time, containing duplicates, scams and posts with planted prompt-injection text.
8. **Data-driven.** Seed data lives in `data/gigsim_seed/` and policy versions in `data/policy_pack/`. A documented loader accepts new job and client files in the same format, so new grader data and the policy change request are data changes, not code changes. GigSim freezes in Phase 2 but policy v2 arrives in Phase 5, so the shape of v2 is drafted before the freeze. The policy, cost and rule schema must be able to express v2 as data alone.
9. **Frozen after acceptance.** When Phase 2 is accepted, `gigsim/` is tagged `gigsim-v1`. From then on, CI fails if anything under `gigsim/` differs from that tag.

# 5. Data Plan

Every dataset choice, the preprocessing, attribution, licences and limitations are documented in `docs/DATA_CARD.md`. Real and synthetic records are always distinguishable: every synthetic record carries `source: synthetic`, and every Kaggle-derived record carries `source: kaggle:<dataset-slug>`.

## Real data (Kaggle; raw files in `data/raw/kaggle/`, git-ignored)
| File | Likely source | Use |
|---|---|---|
| `upwork-jobs.csv` (~53k) | asaniczka/upwork-job-postings-dataset-2024-50k-records | Job text, budgets, hourly ranges, countries → historical jobs, pricing stats, base for the job stream |
| `Final_Upwork_Dataset.csv` (~60k) | ahmedmyalo/upwork-freelance-jobs-60k | Skills and categories, experience level, applicants, payment verified, client spend, rating, feedback count, `Connects_Num` → risk signals, Connects cost |
| `contracts.csv` (~1.3M) | asaniczka/freelance-contracts-dataset-1-3-million-entries | Hourly rate and total paid by job title → fair price bands. It has no client id, so client histories are synthetic, sampled from these distributions. |
| `freelancer_gig_success_dataset.csv` (12k) | sarveshchhetri/freelancer-success-earnings-and-churn-prediction | Persona priors: rates, success rate, response time |
| `processed_labeled_dataset_without_encoding.xlsx` | probably adityammantri/trial-1 | Not inspected yet; decide its use in Phase 1 |
| `Final_Upwork_Dataset.xlsx` | Duplicate of the CSV | Not used |

`asaniczka/all-jobs-on-upwork-200k-plus` is allowed but not downloaded. It is optional.

## Synthetic data (generated, tagged)
- **Three personas** (AI/ML engineer, full-stack web developer, data analyst). Each has:
  - a CV;
  - 15 to 25 case studies;
  - repo READMEs and code;
  - client reviews;
  - about 150 past proposals labelled won, replied or ignored.

  The corpora are deliberately messy:
  - code and prose are mixed;
  - the same project is described three ways;
  - skills are implied rather than named.
- **Hidden client preferences** and client histories.
- **Scam jobs, prompt-injection jobs and duplicates**, mixed into the stream.
- **Client conversations.**
- **Gold labels:** about 200 jobs per persona, each labelled with bid or skip, scam or not, the relevant evidence items, and a fair price band.

## Splits and anti-circularity
We author the simulator, the labels and the agent, so the evaluation could become circular. Two guards prevent that:
- The rules that generate labels and client preferences live only in `data/pipeline/`. They are never copied into `agent/` prompts or config.
- A held-out split is used only for final reporting. It never informs tuning.

The dev set lives in `evals/datasets/`. The instructor's hidden set never enters the repo.

## Licence gate (blocks Phase 1)
Before any derived data is committed, check each Kaggle licence:
- If a licence allows redistribution, the derived seed and dev data are committed.
- If it does not, `make seed` regenerates the data locally from `data/raw/`, and CI uses a small fully synthetic fixture.

# 6. Models

- `agent/config.yaml` has two profiles:
  - `open` (required): open-weight models only, run through Ollama or a hosted open-model provider;
  - `paid` (optional): used only where it beats `open` enough to justify the cost.
- The deployed link works on the `open` profile, through a hosted open-model provider (default Groq, with OpenRouter as fallback).
- Embeddings and the reranker are open models in both profiles (`nomic-embed-text`, `bge-reranker-v2-m3`).
- **Routing by node.**
  - Small model: Scout, Risk Assessor, intent and compliance checks.
  - Strongest affordable model: Writer, Critic, Client Liaison.
  - Every node's model is set in config, never in code.
- At least two open LLM configurations are compared on the dev set before one is chosen. For each profile we report quality, latency and cost: USD for APIs, hardware and tokens per second for local models.

# 12. Risks

- **Grader expectations for "our" GigSim.** The hidden test runs the instructor's jobs and clients against our deployed link, and our seed format is our own invention. Mitigations: the documented loader; ask the instructor early.
- **Circular evaluation.** We author the simulator, the labels and the agent. Mitigations: the anti-circularity rule and the held-out split (§5).
- **Free-tier limits.** Hosted open-model rate limits may throttle the hidden test run. Mitigations: a fallback provider, caching, and small models for frequent nodes.
- **VPS memory.** Postgres, Redis, Langfuse, Ollama and the app on one host. Mitigation: in production use the hosted provider instead of Ollama; Phoenix as the tracing fallback.
- **Scope.** Nine phases for one person. Mitigation: strict phase gates and the smallest version that meets each clause.
