# Software Architecture

Version: 1.1 (X1 agency mode, §15)

# 1. Purpose

This document defines the software architecture for GigBid. It specifies:

- how the project is organized;
- how modules communicate;
- how new features must integrate into the existing codebase.

It is written for both human developers and AI coding assistants. It is the working rulebook. The graded `docs/ARCHITECTURE.md` (diagrams and the reason each agent exists) is written from it in Phase 8.

Order of precedence when decisions conflict:

1. The user's explicit instruction
2. `1.PROJECT_SPECIFICATION.md`
3. This document
4. `3.AI_RULES.md`
5. Existing code

Generated code never overrides this document. If code and this document disagree, flag it and ask; do not silently deviate.

# 2. Architecture Goals

## Simplicity
An intermediate developer should be able to follow the project. Avoid unnecessary abstractions. The smallest design that meets the requirement wins.

## Modularity
Each module performs one responsibility. Modules communicate only through clearly defined interfaces: MCP tools, the marketplace port, Pydantic hand-offs and the HTTP API.

## Loose Coupling
A module must not depend on the internals of another module. Two examples:
- Switching from GigSim to live Upwork changes config, not graph code.
- Swapping a RAG variant changes config, not node code.

## Maintainability
Every feature should be replaceable, testable and debuggable in isolation. Every agent run can be traced and replayed from its checkpoint.

## Extensibility
These future changes must need only small edits to existing modules:
- the platform policy update;
- new grader jobs and clients;
- the signature extension;
- live Upwork mode.

Policies, prompts, models and thresholds are data and config, not code.

## Readability
Readable code is preferred over clever code.

# 4. System Modules

| Module | Single responsibility | Input | Output | Talks to |
|---|---|---|---|---|
| `apps/web` | Show state and collect human decisions | User actions | API calls | `apps/api` only, via generated client |
| `apps/api` | Expose use cases over HTTP and stream graph progress | HTTP requests | Typed JSON, SSE events | Graph services, worker queue, Postgres (via services) |
| `apps/api/auth` | Users, sessions, encrypted OAuth token store | Credentials, OAuth callbacks | Session and tenant id | Postgres |
| `worker` | Run schedules and long graph runs outside web requests | Queue jobs | Graph runs | Redis, `agent/graphs` |
| `agent/graphs` | Wire nodes into the bid and conversation graphs | Initial state | Final or interrupted state | Nodes, checkpointer, store |
| `agent/nodes` | One agent role per file | Typed state slice | Typed hand-off object | LLM (via config), MCP tools, database-free `rag/` code (e.g. `rag/verify.py`) |
| `agent/prompts` | One versioned `.md` prompt per node | — | Prompt text | Loaded by nodes |
| `agent/memory` | Store and promote style and outcome memory | Edits, outcomes | Promoted memory items | LangGraph store |
| `agent/mcp_client.py` | Connect to MCP servers; give each agent only its allowed tools | Server config | Filtered tool lists | MCP servers |
| `agent/marketplace_port.py` | The single marketplace interface | Port calls | Typed results | Adapters |
| `rag/` | Ingest, index, retrieve (variant by config), verify claims | Documents, queries, drafts | Evidence items, claim verdicts | pgvector, BM25 index, LLM |
| `mcp_servers/portfolio` | Read-only evidence tools, resources, prompts | Tool calls | Evidence items | `rag/` |
| `mcp_servers/marketplace` | Marketplace read and write tools with auth, rate limit, idempotency, `dry_run`, audit | Tool calls | Typed results | Marketplace port adapters |
| `mcp_servers/workspace` | Calendar slots, tentative holds, email drafts | Tool calls | Slots, drafts | Local mock store |
| `gigsim/` | Simulate the marketplace and its clients | REST calls | Jobs, clients, outcomes | `data/gigsim_seed/`, `data/policy_pack/`, small LLM |
| `data/pipeline/` | Build seeds, personas and eval sets from raw and synthetic sources | `data/raw/` | `data/gigsim_seed/`, `data/personas/`, `evals/datasets/` | Files only |
| `evals/runners` | Compute metrics and write results | Datasets, running system | `evals/results/*.json` and `*.csv` | API / graphs / GigSim |

Each module performs exactly one responsibility, receives one kind of input, and produces one kind of output.

# 5. Request / Execution Lifecycle

## HTTP request
```
Browser
  ↓
Router (apps/api/routers)
  ↓
Handler (validates with schemas/, resolves the user and tenant)
  ↓
Service (graph service, run service, memory service)
  ↓
Graph / worker queue / Postgres
  ↓
Handler (builds a typed response)
  ↓
Browser
```

## Graph run
```
Worker (schedule or user action)
  ↓
Graph (checkpointed on every step)
  ↓
Node  →  MCP tool  →  MCP server  →  port / adapter  →  GigSim or Upwork
  ↓
interrupt()  (state saved; the UI shows the approval payload)
  ↓
User approves, edits or rejects in the UI  →  API resumes the thread
  ↓
Write tool runs once (idempotency key)
```

Layers are never skipped, and calls only go downward. The lifecycle does not change without updating this document.

# 6. Layer Responsibilities

## Layer 1: Entry (routers, web pages)
**Purpose:** Receive requests.
**Responsibilities:** Define endpoints and pages; hand off to handlers; return responses.
**Forbidden:** Business logic, graph calls, direct database or MCP calls.
**Where:** `apps/api/routers/`, `apps/web/src/app/`.

## Layer 2: Handlers (controllers)
**Purpose:** Coordinate one use case.
**Responsibilities:** Validate the request against `schemas/`, resolve the user and tenant, call one service, build the typed response.
**Forbidden:** Direct SQL, direct MCP or LLM calls, heavy processing.
**Where:** Handler functions in `apps/api/` plus `schemas/`, `auth/` and `streaming.py`.

## Layer 3: Services (agent, RAG, memory, worker)
**Purpose:** Business logic.
**Responsibilities:** Run graphs and nodes, retrieval, claim verification, memory promotion and scheduling.
**Forbidden:**
- Knowing about HTTP request or response objects.
- Generating UI markup.
- Calling GigSim, Upwork or the filesystem directly. Agents use MCP tools only.

**Where:** `agent/graphs/`, `agent/nodes/`, `agent/memory/`, `rag/`, `worker/`.

## Layer 4: Utilities
**Purpose:** Small reusable helpers.
**Rules:** Stateless and framework-agnostic.
**Examples:** Prompt loader, PII masker, idempotency-key builder, injection delimiter, config loader.

## Layer 5: External Systems
**Examples:**
- MCP servers (ours, Upwork, GitHub)
- GigSim
- Postgres (app data, checkpointer, store, pgvector)
- Redis
- Langfuse
- Ollama or a hosted open-model provider

Graph nodes reach the marketplace, the portfolio and the workspace only through MCP tools. MCP servers reach the marketplace only through `MarketplacePort`.

## Cross-cutting: Middleware
Authentication, tenant scoping, trace-id propagation, request logging with PII masking, rate limiting and the central error handler. No business logic.

# 8. Naming Conventions

- **Python files and modules:** `snake_case.py`, named for the role (`bid_graph.py`, `promotion_rules.py`, `v2_hybrid.py`).
- **Node files:** named after the role, as in the starter kit (`agent/nodes/risk_assessor.py`). Each node's prompt has the same base name (`agent/prompts/risk_assessor.md`), with its version in front matter.
- **Python classes:** `PascalCase` (`JobSpec`, `ProposalDraft`).
- **Python functions:** verbs (`extract_job_spec`, `score_fit`); constants are `UPPER_SNAKE_CASE`.
- **TypeScript:** components are `PascalCase.tsx`, other modules `camelCase.ts`, routes follow the Next.js App Router.
- **MCP tools:** `snake_case` verbs (`search_evidence`, `create_proposal_draft`).
- **Config keys:** `snake_case` in `agent/config.yaml`.
- **Variables:** descriptive nouns. No single-letter names outside short loops.

New files follow the same convention as existing ones.

# 9. Data Flow

## Bid graph (one thread per job)
```
Scout queues a job (dedup by job id + content hash)
  ↓
Untrusted-input delimiting of the job post
  ↓
Parallel via Send:  Job Analyst → JobSpec | Risk Assessor → RiskReport | Fit Matcher → FitReport
  ↓
Decision node → BidDecision (skip / watch / bid)    [skip ends the thread]
  ↓
Pricing Strategist → PriceQuote (incl. Connects worth-it)
  ↓
Proposal Writer → ProposalDraft
  ↓
Verifier → claim verdicts; unsupported claims removed or rewritten
  ↓
Critic → Critique  (send back to Writer, at most 2 times)
  ↓
Compliance Guard → ComplianceVerdict (may block with reason)
  ↓
interrupt(): draft, evidence per claim, risk report, price rationale, dry_run preview
  ↓
Approve / edit (diffed → style memory candidate, re-checked by Compliance) / reject with reason
  ↓
submit_proposal via Marketplace MCP (idempotency key) → outcome events → outcome memory candidate
```

## Conversation graph (one thread per client conversation)
```
New client message → delimiting → Client Liaison classifies intent
(question / negotiation / interview request / scam signal)
  ↓
Draft reply and/or Workspace interview slots
  ↓
Compliance Guard
  ↓
interrupt() → approve / edit / reject → send_message (idempotency key)
```

Every step receives one input and produces one output. Only the validated form of data continues through the pipeline.

# 10. Module Boundaries

- Graph nodes never call GigSim, Upwork, a database or a file directly. They call MCP tools obtained from `agent/mcp_client.py`, filtered to that agent's allowlist.
- MCP servers reach the marketplace only through `MarketplacePort`. The graph cannot tell GigSim from Upwork.
- Only the decision node decides bid, watch or skip. Only the Compliance Guard can block a draft.
- Write tools (`create_proposal_draft`, `submit_proposal`, `send_message`) may be called with `dry_run=true` before approval, to build the preview shown in the approval payload. Real writes and Connects spending run only after an approved `interrupt()` resume. Never on any other path.
- Nodes do evidence retrieval only through the Portfolio MCP tool `search_evidence`. From `rag/`, a node may import only code that never touches a database, such as `rag/verify.py` claim splitting and grading.
- Nodes exchange the Pydantic hand-offs in `agent/handoffs.py` for anything a later step decides on, never free text.
- Three things stay apart:
  - **State:** what this job or conversation needs now (`agent/state.py`).
  - **Execution trace:** tool names, arguments, results (Langfuse plus the audit log).
  - **Long-term memory:** promoted items only.
- Long-term memory is written only by `agent/memory/promotion_rules.py`. Raw tool output never goes straight into memory.
- `rag/` does not know about graphs. It takes a query and config, and returns evidence items and claim verdicts.
- `gigsim/` does not import from `agent/`, `rag/` or `mcp_servers/`. It knows nothing about GigBid.
- The rules that generate gold labels and client preferences live only in `data/pipeline/`. They are never copied into `agent/` prompts or config.
- The frontend knows only the generated API client. It never imports backend code.

# 11. Frontend Architecture

```
Next.js App Router pages (TypeScript)
  ↓
Components (EvidenceHover, ApprovalPanel, RunTimeline, ...)
  ↓
Generated API client (src/lib/api, from FastAPI OpenAPI) + SSE subscription
  ↓
Backend
```

- The frontend is independent of backend implementation details. It only knows the API contract.
- **Pending approvals:** they live server-side in the graph checkpoint, so a page refresh never loses one.
- **States and accessibility:**
  - Every screen has empty, loading and error states, including a "marketplace unavailable" banner.
  - Every screen works at phone width and with a keyboard.
- **UI libraries:** no UI framework beyond Next.js and React unless approved. Tailwind is allowed for styling.

# 12. API Conventions

- Every endpoint accepts and returns JSON. The only exceptions are the SSE streams, which use `text/event-stream`.
- **Success responses** are typed Pydantic response models declared on the route (`response_model`), so the OpenAPI schema and the generated TS client stay exact. There is no generic `{success, message, data}` envelope.
- **Error responses** use FastAPI's error shape with a stable code:
  ```json
  { "detail": { "code": "marketplace_unavailable", "message": "The marketplace is unavailable. Your work is queued." } }
  ```
- **Status codes:** 400 or 422 for invalid input, 401 unauthenticated, 403 wrong tenant, 404 missing, 409 conflict (for example, already approved), 429 rate limited, 503 degraded dependency.
- **Request handling:** validate every input; never expose stack traces or internal errors; scope every query by tenant.

# 13. Error Flow

```
Exception (tool timeout, GigSim 429/5xx, LLM failure, validation error)
  ↓
Node / service: bounded retry with backoff → fallback model (cheap nodes) → dead-letter state
  ↓
Graph: step or token budget exceeded → "needs attention" state
  ↓
Handler → central error handler (masked log, trace id)
  ↓
User-friendly response or UI banner (degraded mode: queue the work, recover when the dependency returns)
```

The application never crashes because of user input, and users never see stack traces. When the Marketplace MCP server is down, the UI says so, queues the work and recovers.

# 14. Configuration and Secrets

- `agent/config.yaml` holds:
  - the `open` and `paid` model profiles, with a model per node;
  - the marketplace mode (`gigsim` or `upwork_live`);
  - budgets and thresholds;
  - the active RAG variant;
  - the active policy version.
- Policy rules live in `data/policy_pack/`, and prompts live in `agent/prompts/`. The platform policy update is absorbed by editing these and config, not code.
- Secrets (API keys, OAuth client secrets, the token-encryption key, the DB password) come only from environment variables. `.env.example` lists every variable without real values; `.env` is never committed.
- No hard-coded URLs, keys, model names or magic numbers in modules. Use config or named constants.

# 15. Future Expansion

The architecture leaves room for:
- the signature extension (one of X1 to X6), as new nodes, sub-graphs or MCP tools;
- the policy update and later policy versions (data only);
- new grader jobs and clients (GigSim seed loader);
- live Upwork mode (adapter already behind the port);
- swapping the vector store or tracing tool behind their existing modules.

Adding these should mean adding modules, not rewriting existing ones.

## Signature extension: X1 agency mode (version 1.1, ADR 0006)
- With `Profile.agency` on, a new bid thread's first segment (`apps/api/services/agency.py`, in
  the worker or an API task) runs the Fit Matcher for every persona in `api.personas`, and
  `agent/nodes/router.py` returns a `RouteDecision` naming one member. This step runs before the
  bid graph, because each persona has its own MCP connection.
- The router only picks a member; the decision node still decides bid or skip.
- The graph input carries `member`; resume and retry run as the thread's member, and the board,
  messages and analytics read every member's marketplace data. Off by default.

# 16. Architectural Constraints

Always respected:

- One responsibility per module and per file.
- No circular dependencies.
- No duplicated business logic.
- Layers are not skipped; routers never call graphs, MCP or databases directly.
- No business logic in routers, handlers or middleware.
- No presentation markup generated inside services.
- Modules interact only through their defined interfaces.
- The frontend stays independent of backend internals.
- Agents reach external systems only through MCP tools; MCP servers reach the marketplace only through the port.
- Nothing is sent and no Connects are spent without an approved interrupt.
- Every prompt lives in `agent/prompts/`; every node's model is set in config.
- After the `gigsim-v1` tag, nothing under `gigsim/` changes.
- No secrets in the repo.
- Every number in the README and report traces to a file in `evals/results/`.
